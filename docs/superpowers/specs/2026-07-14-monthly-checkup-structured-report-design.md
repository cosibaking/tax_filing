# 月度经营体检结构化报告与 PDF 导出设计

日期：2026-07-14  
状态：已确认  
适用范围：会员中心「月度体检」页面及会员合规报告接口

## 1. 背景与目标

现有月度体检报告仅保存并展示一段纯文本，无法清晰区分经营数据、资料完整度和风险事项，异常项也没有事实、依据及处理动作。用户需要逐项理解问题，并将结果导出归档或发送给会计、顾问。

本次改造目标：

1. 将体检结果改为可追溯的结构化报告，同时保留纯文本摘要兼容现有数据。
2. 按业务类别展示检查结果，突出异常和待处理事项。
3. 每个异常项完整说明异常事实、判断依据、可能影响、处理建议、所需材料、处理期限和人工复核要求。
4. 支持将指定报告版本导出为 PDF。
5. 已发布版本保持不可变；重新体检必须创建新版本。

首版不包含 Excel 导出、在线编辑报告、自动提交税务申报、自动判定违法违规或自动生成最终申报数字。

## 2. 方案选择

### 方案 A：继续生成纯文本，前端按段落切分

改动小，但字段含义依赖文本格式，异常无法稳定排序、筛选和导出，后续扩展成本高，不采用。

### 方案 B：后端返回结构化报告，前端分类渲染，PDF 使用同一快照生成

页面和 PDF 共用同一份结构化数据，报告版本可追溯，规则和展示职责清晰。需要新增结构定义、数据迁移和 PDF 生成器，改造量适中。

### 方案 C：由大模型直接生成 HTML/PDF

表现灵活，但输出结构、分页和内容稳定性不足，也不利于安全审计，不采用。

采用方案 B。确定性规则负责形成检查项和风险等级，叙述层只负责将结构化事实转成易读文字，不允许大模型改变检测事实或风险等级。

## 3. 页面信息架构

### 3.1 顶部操作区

- 账期选择器。
- 「生成新版本」按钮。
- 每个报告版本显示版本号、状态和生成时间。
- 「导出 PDF」按钮：草稿和已发布版本均可导出，导出内容固定对应当前版本。
- 草稿显示「确认并发布」按钮；已发布版本不显示修改类操作。

### 3.2 报告总览

展示三个摘要指标：

- 体检结论：正常、需关注、需尽快处理。
- 资料完整度：百分比及主要缺失项。
- 风险分布：高、中、低风险数量。

结论按确定性规则计算：存在高风险为「需尽快处理」；无高风险但存在中风险为「需关注」；其他为「正常」。资料不足本身作为检查结果呈现，不把未知数据错误地判定为正常。

### 3.3 分类展示

报告固定包含以下分类，分类内没有数据时也应展示「未发现异常」或「资料不足」，避免用户误以为系统漏检：

1. 经营数据：收入、支出、开票、回款及匹配情况。
2. 资料完整度：银行流水、发票、合同、工资和社保材料。
3. 税务与申报：当前账期待办、临近截止日和逾期情况。
4. 资金与股东往来：公司与个人账户转账、股东投入和借款待确认事项。
5. 用工与社保：员工、工资、个税、社保和公积金资料。
6. 工商与年度事项：工商年报、企业信息更新和年度事项。

页面默认先显示总览和异常清单；分类入口用于定位完整检查结果。异常按高、中、低风险排序，同等级按处理期限升序排列。

### 3.4 异常详情

每个异常项必须包含：

- 异常标题和所属分类。
- 风险等级：high、medium、low。
- 异常事实：仅陈述已确认数据和缺失资料。
- 判断依据：规则编码、触发条件和实际检测值的用户可读说明。
- 可能影响：使用「可能」「建议确认」等审慎措辞。
- 处理建议：可执行的下一步动作。
- 所需材料：需要上传或核验的资料清单。
- 处理期限：规则给出日期时显示日期，否则显示「建议尽快处理」。
- 人工复核：是否建议人工复核。

首版异常详情仅提供「补充材料」和「申请人工复核」入口，不增加独立的异常处理状态机。「补充材料」跳转经营资料库；「申请人工复核」跳转人工服务并携带报告 ID 和异常编码。

## 4. 结构化数据模型

新增报告结构 `StructuredReport`：

```text
StructuredReport
├── schemaVersion
├── summary
│   ├── conclusion
│   ├── completenessRate
│   ├── highCount / mediumCount / lowCount
│   └── dataNotice
├── categories[]
│   ├── code / name / status
│   ├── summary
│   └── checks[]
└── anomalies[]
    ├── code / categoryCode / title / severity
    ├── facts / basis / impact / recommendation
    ├── requiredMaterials[]
    ├── dueDate
    ├── requiresManualReview
    └── ruleVersion
```

`schemaVersion` 首版为 `1`。服务端不得信任前端提交的结论或异常描述，而是根据当前输入快照生成结构化结果。

数据库表 `xy_compliance_monthly_report` 新增 `structured_json` JSON 字段，保存该版本的完整结构化结果。原有 `statistics_json`、`completeness_json`、`risk_snapshot_json` 和 `content` 继续保留：

- 三个输入快照用于审计生成依据。
- `structured_json` 是页面和 PDF 的唯一结构化展示源。
- `content` 保存兼容摘要，供旧客户端或历史逻辑使用。

新增 MySQL 与 PostgreSQL 迁移脚本，迁移只新增可空字段，不重写历史数据。历史报告没有 `structured_json` 时，接口返回兼容结构：将原 `content` 作为「历史报告摘要」，并提示该版本不包含明细；PDF 仍可导出摘要。

## 5. 后端组件与数据流

### 5.1 报告生成器

将现有生成逻辑拆成三个边界清晰的部分：

1. `Builder`：读取 `Input`，生成分类检查项、异常详情和汇总指标。
2. `Renderer`：将结构化结果生成兼容文本摘要。
3. `PDFGenerator`：根据持久化的报告快照生成 PDF 字节。

生成流程：

```text
前端提交账期及已确认数据
→ 服务端校验账期和输入
→ Builder 生成 StructuredReport
→ Renderer 生成 content
→ 同一事务保存输入快照、结构化报告和版本号
→ 返回完整报告
```

叙述模型可作为后续增强，但首版不能覆盖 `Builder` 生成的事实、风险等级、规则依据和处理期限。

### 5.2 PDF 导出

新增会员接口：

```http
GET /compliance/reports/{id}/pdf
```

请求路径参数：

- `id`：月度体检报告 ID，正整数。

成功响应：

- `Content-Type: application/pdf`
- `Content-Disposition: attachment; filename="monthly-checkup-2026-07-v2.pdf"`
- 响应体为 PDF 二进制。

错误响应示例：

```json
{
  "code": -1,
  "message": "报告不存在或无权访问"
}
```

导出服务必须按当前会员 ID 查询报告，禁止通过 ID 越权读取其他会员数据。PDF 直接使用数据库中该版本的 `structured_json`，不得使用最新业务数据重新计算，从而保证导出内容与页面版本一致。

PDF 内容顺序：报告标题与版本、企业及账期信息、结论摘要、分类结果、异常详情、生成时间和免责声明。异常详情支持自动分页，单个异常跨页时重复必要的小标题。首版复用项目现有 GoPDF 和内嵌中文字体，不依赖浏览器截图。

## 6. 前端组件设计

`reports.vue` 负责获取版本列表和页面编排，报告展示拆为局部组件，避免继续扩大单文件职责：

- `ReportSummary`：结论、资料完整度和风险分布。
- `ReportCategories`：分类入口及分类检查结果。
- `ReportAnomalyList`：异常排序、摘要和详情展开。

前端 API 类型新增 `StructuredReport`、`ReportCategory`、`ReportCheck` 和 `ReportAnomaly`。导出按钮使用带鉴权的请求获取 Blob，再创建临时下载链接；不能直接 `window.open` 受鉴权保护的接口。

页面兼容历史数据：若 `structuredReport` 为空，展示现有 `content`，同时显示「历史版本仅包含摘要」提示。生成、发布和导出操作分别维护独立 loading 状态，避免重复请求。

## 7. 错误处理与安全边界

- 账期必须符合 `YYYY-MM`，非法输入返回明确错误。
- 生成版本时使用数据库事务或唯一约束处理并发版本号冲突。
- 报告不存在或会员不匹配统一返回「报告不存在或无权访问」。
- 结构化 JSON 损坏时页面降级显示 `content`，导出返回可理解错误并记录结构化日志。
- PDF 生成失败不修改报告状态，也不生成空文件。
- 用户可见内容不得使用「已违法」「一定正确」等确定性合规结论。
- PDF 文件名只使用服务端生成的账期和版本号，避免文件名注入。

## 8. 测试与验收

### 后端单元测试

- 空数据生成「资料不足」而不是「正常」。
- 高、中、低风险统计和总体结论正确。
- 异常详情字段完整，缺失可选值时使用明确默认文案。
- 分类固定且排序稳定，异常排序符合风险和期限规则。
- 历史纯文本报告可正常读取和导出。
- PDF 以 `%PDF` 开头，包含非空内容且多异常可分页。
- 导出接口拒绝访问其他会员的报告。
- 已发布报告仍不可修改，新生成报告版本递增。

### 前端测试与验收

- 有异常、无异常和资料不足三种状态均能正确展示。
- 六个分类清晰，异常详情完整且移动端不溢出。
- 草稿和已发布报告都能导出 PDF。
- 导出失败展示错误提示，按钮恢复可用。
- 历史报告正常降级，不出现空白页面。

### 提交前验证

- Go 单元测试、格式化、静态检查和编译。
- Web 端 lint、类型检查和生产构建。
- 执行迁移后验证报告生成、发布、PDF 下载和历史报告兼容。

## 9. 影响范围与回滚

影响范围包括会员月度体检页面、会员报告 API、报告生成逻辑、报告表结构、PDF 生成模块和接口文档，不影响现有对账单 PDF、收入台账、费用台账及税务申报流程。

回滚代码时可恢复旧页面和旧接口实现。新增数据库字段允许保留，不影响旧版本运行；如必须回退数据库，只能在确认没有新版本依赖后删除新增字段，禁止删除报告数据。部署前备份数据库结构，生产配置不做强制覆盖。
